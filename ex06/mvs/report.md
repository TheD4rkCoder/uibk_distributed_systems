## Task 1 - Dapr

### Implementation

4 processes, each with its own daprd sidecar: coordinator, sensor-1, sensor-2, sensor-3

```
sensor-1 ┐
sensor-2 ├── publish {run, sensor, seq, value} ──> topic measurements (pubsub.redis) ──> coordinator ──> statestore (state.redis)
sensor-3 ┘
```

sensor: one main with the sensor id as argument, sends its 4 readings to the topic with a 500-1000 ms sleep before each

every message carries the run id (set by run.sh for all 4 processes) and the index of the reading (seq)

```kotlin
READINGS.getValue(id).forEachIndexed { seq, value ->
    Thread.sleep(Random.nextLong(500, 1001))
    val message: Measurement = mapOf(
        "run" to RUN_ID, "sensor" to id.toLong(), "seq" to seq.toLong(), "value" to value.toLong(),
    )
    client.publishEvent(PUBSUB, TOPIC, message).block()
}
```

coordinator: streaming subscription (`DaprPreviewClient.subscribeToTopic`), so no http server / spring app is needed for receiving events

| state key | value |
| :--- | :--- |
| **sensor-1..3** | `SensorState(latest, state, lastSeq)`, state NORMAL / ALERT |
| **alerts** | number of active alerts |
| **processed** | number of processed measurements |

dapr prefixes the keys with the app id, in redis they are `coordinator||sensor-1` etc

all keys are reset on start, every measurement is a read-modify-write of the sensor key and both counters, written back in one state transaction so the counter and the sensor states can't get out of sync

messages from another run (left in the redis stream by an aborted run) and redelivered duplicates (pub/sub is at-least-once) are ignored before anything is changed

```kotlin
if (m["run"] != RUN_ID || id !in 1..3 || seq == null || value == null) {
    System.err.println("ignored stale message $m")
    return processed
}
val prev = read(client, "sensor-$id", SensorState::class.java)
if (seq <= prev.lastSeq) {
    System.err.println("ignored duplicate sensor $id seq $seq")
    return processed
}
```

```kotlin
val next = if (value > THRESHOLD) "ALERT" else "NORMAL"
println("Sensor $id: $value -> $next")
if (prev.state != next) {
    alerts += if (next == "ALERT") 1 else -1
    println("Active alerts: $alerts")
}
client.executeStateTransaction(STORE, listOf(
    upsert("sensor-$id", SensorState(value, next, seq)),
    upsert("alerts", alerts),
    upsert("processed", processed),
)).block()
```

the counter only changes when the state flips (NORMAL -> ALERT +1, ALERT -> NORMAL -1), so 81 -> 85 on sensor 2 doesn't count twice

events are handled one after another (`publishOn(boundedElastic)`), the handler also runs in `synchronized(lock)` so the read-modify-write can't interleave

`takeUntil { processed >= 12 }` ends the subscription after 12 accepted measurements, then the summary is read back from the state store

the pubsub component has `concurrency: 1`, otherwise daprd hands a backlog of messages to the app in parallel and a sensor's readings can arrive out of order (seen in a test: 45, 55, 78, 62)

the coordinator is started 8 s before the sensors only so its line comes first, messages published before it subscribes are not lost (the redis consumer group reads the stream from the start, tested below)

## Task 2 - CSM/CSML

### Implementation

one csml file (src/uc4.pkl) with 2 state machine definitions and 4 instances

```
instances {
  ["coordinator"] { stateMachineName = "coordinator" }
  ["sensor1"] { stateMachineName = "sensor"; data { ["id"] = "1"; ["values"] = "[45, 62, 78, 55]" } }
  ["sensor2"] { stateMachineName = "sensor"; data { ["id"] = "2"; ["values"] = "[52, 81, 85, 60]" } }
  ["sensor3"] { stateMachineName = "sensor"; data { ["id"] = "3"; ["values"] = "[40, 48, 73, 80]" } }
}
```

every instance runs in its own cirrina container (RUN=coordinator / sensor1 / ...), events go over a zenoh router, persistent data is in etcd

| data | scope | where |
| :--- | :--- | :--- |
| **activeAlerts, processed** | persistent (collaborative state machine) | etcd |
| **latest, states** (maps sensor -> value / NORMAL, ALERT) | transient (coordinator) | coordinator instance |
| **id, values** (measurement list) | transient, set per instance in the instances block | sensor instance |
| **i** (next reading) | transient (sensor) | sensor instance |

sensor: init -> hello -> waiting -> emitting -> waiting ... -> done

hello is a handshake: the sensor sends ready to the coordinator every second until the coordinator answers go, zenoh doesn't keep events for a coordinator that isn't running yet, so without it a late coordinator loses readings and never finishes

```
["hello"] = new State {
  entry {
    new Emit { event { topic = "ready"; data { ["sensor"] = "id" } }; target = "'coordinator'" }
  }
  after {
    ["retry"] = new Timeout {
      delay = "1000"
      triggers = new Emit { event = new Internal { topic = "retry" } }
    }
  }
  on {
    ["retry"] { to = "hello" }
    ["go"] { to = "waiting" }
  }
}
```

waiting has a Timeout of `std:randomAround(750, 250)` ms that raises an internal tick, emitting sends the measurement to the coordinator and goes back to waiting while readings are left

```
["emitting"] = new State {
  entry {
    new Emit {
      event { topic = "measurement"; data { ["sensor"] = "id"; ["value"] = "values[i]" } }
      target = "'coordinator'"
    }
    new Eval { expression = "i = i + 1" }
  }
  always { new Transition { to = "waiting"; provided = "i < size(values)"; or = "done" } }
}
```

coordinator: init (reset counters) -> monitoring -> finished

in monitoring, ready is answered with go to that sensor, a measurement is an internal transition, a Match picks the case: NORMAL -> ALERT, ALERT -> NORMAL or no change (default only logs)

```
new Case {
  of = "$value > 70 && states[$sensor] == 'NORMAL'"
  yields {
    new Eval { expression = "states[$sensor] = 'ALERT'" }
    new Eval { expression = "activeAlerts = activeAlerts + 1" }
    new Log { message = "'Sensor ' + $sensor + ': ' + $value + ' -> ALERT'" }
    new Log { message = "'Active alerts: ' + activeAlerts" }
  }
}
```

a state machine instance handles its events one at a time (cirrina puts them in one queue per instance), so no lock is needed for the counter

after the 12th measurement the coordinator raises an internal allProcessed event and goes to the terminal state finished, which logs the summary

## Discussion Questions

>Question 1: How did the amount of infrastructure boilerplate code differ between Dapr and CSML?

dapr: maven pom, two component yamls, a sidecar per process with its own ports, client setup (waitForSidecar, preview client for subscriptions), TypeRef for the payload type, Jackson needs a no-arg constructor for the state class and boxed Integer instead of int

csml: no client code at all, Emit with a target and an on transition is the whole communication, but the deployment needs etcd, a zenoh router, a zenoh config file and one container per instance

the csml file has more lines (129 vs 97) because Pkl is very nested and every log, assignment and branch is its own action block, but all of it is application logic

>Question 2: How does CSM's hierarchical data scoping (persistent vs. transient data) compare to explicitly managing state keys in Dapr?

dapr: flat key value store, I pick the keys, read them, change them in kotlin and write them back myself, consistency (transaction, lock) is my job

csml: variables are declared in the scope where they belong and used like normal variables in expressions, the runtime reads and writes them

persistent data goes to etcd and is visible to every instance, transient data stays in the instance, so the per-sensor maps are transient in the coordinator and only the counters are persistent

persistent values are read as a deserialized copy, so changing an element of a persistent map (`m[k] = v`) would only change the copy, only whole-variable assignments are stored, that's why the maps are transient

>Question 3: Which programming model felt more natural for expressing cross-component coordination, and why?

csml for the coordinator: NORMAL / ALERT is already a state machine, the Match cases are the transitions from the spec, and events are handled one at a time per instance so there is no locking

dapr for the sensor: a for loop with a sleep is shorter and clearer than 4 states with a timeout and an index variable

dapr took 5 hours of total reading and programming/prompting, it ran correctly on the first try in the normal case, but the tests found 3 bugs in it (stale messages, ordering, crash on an old message format), csml took only 3 hours but needed 2 fixes to run at all (amd64 image, termination) and 1 after testing (late coordinator)

>Question 5: What were the main difficulties encountered when implementing your assigned use case in each framework?

dapr: the redis stream and consumer group outlive a run, so messages from an aborted run are replayed into the next one, fixed with a run id in every message; at-least-once delivery means duplicates are possible, fixed with seq per sensor; ordering is not guaranteed when daprd delivers a backlog concurrently, fixed with `concurrency: 1`; payload and state typing through Jackson without the kotlin module

csml: termination, the `always { provided = "processed == 12" }` transition in monitoring never fired, always transitions are only checked when the state is entered (StateMachine.kt in cirrina), not after an internal transition, replaced by an internal allProcessed event; zenoh drops events nobody is subscribed to, so a coordinator that starts late misses readings, fixed with the ready / go handshake; docs say ZENOH_EVENT_HANDLER_CONFIG_URI is `tcp://zenoh:7447` but cirrina loads it as a config file path, so a zenoh.json5 is mounted; persistent variables survive in etcd if the etcd container isn't removed, so the coordinator resets them in init
